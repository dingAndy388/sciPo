====== 游戏设计指导手册 ======

===== 前言 =====

这个文档是我和deek一起撰写的，主要是注意到各设计师经验有限，却也学业繁忙，无论是在设计理论，团队协作（你们设计部是唯一有“团队”来协作的地方）还是写作格式上都有一定不足。

你们是游戏开发中的绝对核心，代码优化差不过多加载几秒，只有游戏设计是游戏的根基，你们才是史诗的谱写者。

要创作出环环相扣引人入胜的机制和情节必然不易，可要各位IB学生花一两个月去学习设计理论显然是痴心妄想。于是便有了这篇文档，意在短时间内帮你们完成知识上的统一和核心概念的学习。让我们避免设计随着时间变得混乱，矛盾，最终陷入难以爬出的泥潭。

记住，你们是游戏背后的最大功臣，没有玩家会记住代码是谁写的，但好的设计会永远存在玩家的心中。

**鉴于个别策划对本文档的蔑视，现执行惩罚机制，如违反此文档内容者母亲数量减一**


===== 1. 核心设计原则 =====

无论设计什么内容，请用以下原则来衡量它的合理性。如果一个设计违背了这些原则，要么修改它，要么准备好充分的理由。

==== 1.1 简单规则，复杂涌现 ====

游戏的底层机制应该足够简洁，但通过不同机制的组合，能产生丰富的策略变化。

- **好例子**：象棋（6种棋子、简单规则）→ 无数种棋局。

- **坏例子**：每个建筑有15种专属规则，玩家需要背诵手册才能玩。

- **自检问题**：我能用一句话说清楚这个机制吗？

==== 1.2 有意义的抉择 ====

给玩家的每个选项都应该是真正的选择，而不是伪装成选择的“更好/更坏”。

- **好抉择**：是现在收获少量粮食应急，还是等待三个月后的大丰收？（风险 vs 回报）

- **坏抉择**：选项A：获得10金币；选项B：获得5金币。（没人会选B）

 - **自检问题**：不同风格的玩家会做出不同的选择吗？有没有“必选项”？

==== 1.3 反馈即奖励 ====

玩家的每一个操作，都必须在0.5秒内获得清晰的反馈。

- **视觉反馈**：按钮按下效果、资源数字变化、伤害飘字。

- **听觉反馈**：点击声、获得物品声、警告音。

- **状态反馈**：建筑正在建造中（进度条）、单位正在移动（路径显示）。

- **自检问题**：如果我做了这个操作，我怎么知道它生效了？

==== 1.4 一致性 ====

相同类型的交互，在整个游戏中应该保持一致的逻辑和表现。

- **例子**：如果“取消”按钮在建造界面是红色、在右下角，那么在科技界面、事件界面也应该是红色、在右下角。

- **自检问题**：玩家需要重新学习这个界面的操作吗？

==== 1.5 失败也是体验 ====

玩家会失败，这没关系。但失败应该提供信息，而不是单纯的惩罚。

- **好失败**：“你因粮食耗尽而灭亡。提示：在冬季来临前，每个农民需要储备200单位食物。”

- **坏失败**：“你输了。重新开始吧。”

- **自检问题**：玩家能从这次失败中学到什么，下次玩得更好？

==== 1.6 可维护性 ====

设计要便于后续修改和扩展。避免硬编码、避免过于复杂的耦合。

 - **自检问题**：如果三个月后要调整这个数值，我需要改几个地方？

===== 2. 系统框架：把机制编织成网 =====

分散的设计只是碎片，只有连接起来才能成为游戏。本节帮你建立“系统性思维”。

==== 2.1 核心循环图 ====

**在开始任何具体设计之前，必须先定义核心循环。** 把它贴在wiki首页，每次设计新内容时问：它作用于哪个环节？

一个典型的策略沙盒核心循环：

    [探索] → [采集] → [建造/制作] → [生存/防御] → [解锁更强探索能力] → [探索更危险区域]
      ↑                                                                ↑        
      └────────────────────────────────────────────────────────────────┘

**任务**：画出我们这个游戏的核心循环图（建议用Miro或Draw.io），并确保每个设计都能在循环中找到位置。

==== 2.2 机制依赖关系 ====

用一张图展示主要系统之间的影响方向。这能帮你发现“改了A会炸掉B”的隐藏风险。

**示例依赖关系**（用箭头表示“影响”）：

    [时间流逝] → [事件触发概率] → [资源产出] → [科技研发速度] → [建筑解锁] → [事件池变化]

**任务**：列出我们游戏的所有主要系统（时间、资源、科技、事件 等），画出它们之间的依赖关系图。

==== 2.3 设计检查清单 ====

每设计一个新内容（科技、事件、建筑、单位等），必须填写以下清单：

| 问题 | 你的答案 |
| 它作用于核心循环的哪个环节？ |   |
| 它依赖哪些已有系统？ |   |
| 它影响哪些其他系统？如何影响？ |   |
| 它与哪些现有内容可能产生联动？ |   |
| 如果删除它，核心循环是否受损？ |   |
| 它提供什么样的玩家体验？（紧张/成就感/策略思考等） |   |

===== 3. 内容生产指南 =====

面对几十个事件、上百个科技节点，靠“灵感爆发”是填不满的。本节提供批量生产的工业化方法。

==== 3.1 标准化模板 ====

所有设计必须按模板填写，便于批量导入和后期维护。

=== 示例（只是示例，具体模板自行设计） ===

**3.1.1 随机事件模板**（Excel列名）

| 字段 | 说明 | 示例 |
| ID | 唯一标识，格式：EVENT_XXX | EVENT_FLOOD_01 |
| 名称 | 事件标题 | 洪水来袭 |
| 触发条件 | 满足什么条件才会出现此事件 | 回合>10 & 拥有河流 & 未拥有“堤坝”科技 |
| 权重 | 相对出现概率（1-10） | 5 |
| 描述文本 | 展现给玩家的情景文字 | 连日暴雨，河水暴涨，低洼处的农田面临被淹的危险。 |
| 选项A_文本 | 选项描述 | 组织村民加固堤坝 |
| 选项A_消耗 | 执行此选项消耗什么 | 木材：50，人力：20 |
| 选项A_成功率 | 成功概率（0-100），留空表示100% | 80 |
| 选项A_成功效果 | 成功时获得什么 | 民心+10，避免损失 |
| 选项A_失败效果 | 失败时发生什么 | 木材损失，农田减产30% |
| 选项B_文本 | 选项描述 | 放弃农田，向高处转移 |
| 选项B_消耗 | ... | ... |
| 选项B_效果 | ... | 损失农田，但人口安全 |
| 选项C_特殊条件 | 需要什么才能出现此选项 | 拥有“水利工程”科技 |
| 选项C_效果 | ... | ... |
| 影响链条 | 此事件可能引发的后续影响 | 如果选择加固且成功，后续事件“感谢河神”出现概率+20% |

| 名称 | 科技名称 | 铁器冶炼 |
| 领域 | 军事/经济/文化/奇观等 | 军事 |
| 时代 | 早期/中期/晚期/终极 | 中期 |
| 前置科技1 | 必须已研发的科技 | TECH_MINING |
| 前置科技2 | 可选第二个前置 | TECH_FIRE |
| 消耗科研点 | 研发所需点数 | 150 |
| 消耗资源 | 额外消耗的资源 | 铁矿：20 |
| 研发时间 | 所需回合数/秒数 | 5回合 |
| 解锁内容1 | 解锁的建筑/单位/配方 | 铁剑兵 |
| 解锁内容2 | ... | 铁矿矿井 |
| 被动效果 | 研发后永久生效的增益 | 所有单位攻击力+10% |
| 描述文本 | 科技说明 | 掌握了铁的冶炼技术，武器更加锋利。 |
| AI权重 | 电脑对手研究此科技的倾向 | 80 |
| 影响链条 | 此科技影响的现有事件/机制 | 随机事件“武器生锈”不再发生；“铁器时代”事件出现 |

**3.1.3 资源模板**

| 字段 | 说明 | 示例 |
| ID | 唯一标识，格式：RES_XXX | RES_WOOD |
| 名称 | 资源名称 | 木材 |
| 类型 | 基础/高级/稀有/抽象 | 基础 |

| 稀有度 | 影响出现概率/数量 | 常见 |
| 描述 | 资源说明 | 最基本的建筑材料，用于建造和制作。 |

==== 3.2 批量创意思维工具 ====

**3.2.1 排列组合法**（用于随机事件）

公式：**情境 × 资源 × 抉择 = 事件雏形**

- **情境库**：丰收、灾害、入侵、发现、内乱、贸易、庆典、迁徙、瘟疫、技术突破

- **资源库**：食物、木材、石料、金币、人口、民心、士气、科研点、健康度、信仰

- **抉择库**：投资眼前、投资长远、冒险一搏、保守求稳、合作共赢、零和博弈

**操作步骤**： 
  - 列出现有资源列表（至少5-10种） 
  - 列出常见情境（至少5-8种）
  - 随机组合，生成事件标题 
  - 根据标题填充模板细节

**示例**：丰收（情境）+ 民心（资源）+ 冒险一搏（抉择）= 事件“大丰收”：今年粮食吃不完，是酿酒庆祝（消耗粮食，可能获得更多民心，也可能引发治安问题），还是修建粮仓（消耗部分粮食，获得永久存储上限，稳定民心）？

**3.2.2 维度拆解法**（用于科技树）

公式：**领域 × 时代 = 科技树网格**

- **领域**：军事、经济、文化、奇观、航海、魔法、工业…… 
- **时代**：早期、中期、晚期、终极

**操作步骤**： 
  - 确定3-5个核心领域 
  - 每个领域划分3-4个时代阶段 
  - 每个格子填充3-5个科技 
  - 总科技数 ≈ 领域数 × 时代数 × 3~5

**示例**：

| 领域 | 早期 | 中期 | 晚期 | 终极 |
| 军事 | 石制武器、 basic训练 | 铁器、弓箭、战车 | 骑兵、攻城器、军事工程 | 火药、军事学院、总动员 |
| 经济 | 轮作、采矿、贸易 | 货币、商路、会计 | 银行、公司、税收 | 工业化、全球贸易 |
| 文化 | 文字、祭祀 | 哲学、艺术 | 教育、印刷 | 大众传媒、意识形态 |

**3.2.3 极端情况测试**

设计完成后，模拟两个极端场景：

- **“天选之子”场景**：所有随机事件都出正面，所有科技都快速研发。游戏会不会变得太简单、太无聊？ 
- **“倒霉蛋”场景**：连续触发最坏事件，关键科技被卡。游戏会不会陷入死局，无法翻盘？

如果任一场景导致体验崩溃，需要添加“保底机制”或“负反馈调节”（例如连续失败后增加成功概率）。

==== 3.3 联动矩阵 ====

当内容数量超过20个后，必须用矩阵记录它们之间的互动关系。这能防止后期出现逻辑矛盾。

**示例：科技-事件联动矩阵（部分）**

|   | 事件A：洪水 | 事件B：丰收 | 事件C：铁矿发现 | 事件D：叛乱 |
| 科技1：水利工程 | 触发概率-50%，选项成功率+30% | - | - | - |
| 科技2：良种培育 | - | 产出+50%，新选项“推广良种” | - | - |
| 科技3：探矿术 | - | - | 触发概率+100% | - |
| 科技4：常备军 | - | - | - | 触发概率-80%，镇压选项成功率+50% |

**操作建议**： 
  - 在Excel中建立两个轴：横轴是所有事件，纵轴是所有科技/建筑/单位 
  - 每新增一个内容，遍历另一轴，填写可能的影响关系 
  - 没有影响就留空

===== 4. 版本规划与迭代节奏 =====

不要试图一次性做完所有内容。分阶段推进，每个阶段都有明确目标。

==== 4.1 最小可行产品（MVP）定义 ====

第一个可玩版本的目标是**验证核心循环**，而不是堆砌内容。例如，MVP只需要：

- **核心资源**：2-3种（如食物、木材、人口） 
- **科技树**：2条分支，每条3-5个节点，覆盖从早期到中期 
- **随机事件**：5-10个，能够展示事件系统的基本逻辑 
- **建筑/单位**：能完成核心循环的最小集合（如农场、伐木场、简易住所）

**MVP检查清单**：
  - [ ] 玩家能从开始状态，通过一系列操作，进入下一个发展阶段吗？
  - [ ] 核心循环转了至少两圈吗？（探索→采集→建造→探索）
  - [ ] 有明确的胜利/失败条件吗？
  - [ ] 没有严重bug导致无法进行吗？

==== 4.2 内容里程碑 ====

MVP之后，分阶段扩充内容。每个阶段有明确的主题。

| 阶段 | 主题 | 目标内容量 | 完成标准 |
| Alpha 1 | 经济系统完善 | 资源扩展到5种，经济类科技20个，经济事件15个 | 玩家可以体验完整的经济发展和资源管理 |
| Alpha 2 | 军事冲突深化 | 军事科技15个，战斗单位5种，战斗事件10个 | 可以体验完整的战斗流程和战损管理 |
| Alpha 3 | 文化与外交 | 文化科技15个，外交选项5种，文化事件15个 | 非暴力胜利路径可行 |
| Beta | 内容总量达标 | 全部科技80-100个，全部事件50-60个 | 所有预设内容已实现，无重大缺失 |
| 正式版 | 平衡性打磨 | 同上，但数值经过多轮调整 | 各流派胜率接近，无破坏性bug |

==== 4.3 平衡性迭代流程 ====

**初版数值**：凭经验和直觉填写，标记为“待调整”
**内部测试**：开发团队自己玩，记录明显失衡点
**数据收集**：记录玩家行为（科技选择频率、事件触发次数、资源曲线）
**批量调整**：在Excel中批量修改数值（避免手动一个个改）
**回归测试**：确认修改没有引发新问题
**循环**：重复2-5，直到满意

**重要**：数值不是一次就能定死的，预留通过配置文件批量修改的接口。

===== 5. 协作与沟通规范 =====

多人协作时，清晰的流程比个人能力更重要。

==== 5.1 唯一事实源 ====

- **所有设计数据，以wiki/共享Excel为准**。

- 开发只从这里读取数据，不接受口头或私聊发来的修改。

- 任何修改必须更新文档，并在通知所有人。

==== 5.2 文件命名与版本 ====

- 文件命名格式：`[系统]_[内容类型]_[版本号].xlsx`

  - 示例：`Core_Events_v0.2.xlsx`

- 每次重大修改，复制一份并增加版本号，保留历史记录 - 最终确认可用的版本，标记为 `_FINAL`

==== 5.3 设计评审会 ====

定期执行，时长不超过1小时。

**需要评审的关键设计**：
  - 涉及核心机制的重大更改
  - 涉及机制底层的重大改动
  - 有关设计纲领原则的更改
  - 存在意见分歧的设计想法
  - 涉及多个部门协作的设计

**会议流程**： 

1. **会前**：

设计师将有争议性的待评审设计文档链接发给相关人士（开发美工、音乐……），注明“待评审” 

2. **会上**：

  - 设计师简要介绍设计
  - 相关成员评估实现成本和技术风险
  - 主策/制作人评估设计方向和体验
  - 讨论修改方案
  - 明确修改责任人+截止时间

3. **会后**：修改后的文档重新上传，关闭评审议题

**评审要点**： 
  * 设计是否符合核心原则？ 
  * 实现成本是否可控？ 
  * 是否存在与其他系统的冲突？ 
  * 是否有明确的验收标准？

===== 7. 常见问题与陷阱 =====

==== Q1：我设计的这个事件/科技，玩家真的会注意到吗？ ====

**A**：如果它没有明显的视觉/听觉/数值反馈，玩家很可能注意不到。确保每个设计都有“存在感”——要么改变资源数值，要么弹出提示，要么解锁新内容。

==== Q2：我担心某个设计太强/太弱，但不确定怎么办？ ====

**A**：标记为“待测试”，先做出来。在测试阶段通过数据判断，不要在设计阶段过度纠结。记住：能通过数据调整的问题，都不是大问题。

==== Q3：两个设计师的设计冲突了怎么办？ ====

**A**：回到核心循环图和机制依赖图，看哪个设计更符合整体框架。如果都有道理，提交评审会讨论决定。**不要私下妥协**，否则后续维护会乱。

==== Q4：设计太多了，感觉填不完怎么办？ ====

**A**：先做MVP，再做Alpha 1、Alpha 2……分解任务。每天填3个事件模板，一个月就是90个。用排列组合法批量生成，比苦思冥想高效。

==== Q5：我想到一个特别酷的设计，但它不符合核心循环怎么办？ ====

**A**：两个选择： 1. 修改核心循环，把新设计纳入（需要团队讨论，影响较大） 2. 把设计存到“创意池”，等后续版本再考虑（如果它真的足够酷，迟早会用上）

===== 8. Wiki 写作规范（DokuWiki 语法版） =====

为了保证 wiki 页面能被开发直接使用，也为了让所有设计内容可维护、可追溯，本节规定统一的写作规范。所有设计相关页面（事件、科技、建筑、资源等）必须遵循以下格式。

---

==== 8.1 页面基本结构 ====

每个设计页面必须包含以下五个部分，按顺序排列：

<code>
// 负责人：@用户名
// 最后更新：YYYY-MM-DD
// 标签：{{tag>标签1 标签2}}

===== 页面标题 =====

=== 概述 ===
（1-2句话说明核心作用）

=== 数据表 ===
（使用wiki表格，每行一个条目）

=== 联动说明 ===
（列出与其他系统的联动关系）

=== 变更记录 ===
^ 日期 ^ 修改人 ^ 修改内容 ^
| ... | ... | ... |
</code>

=== 8.1.1 元信息 ===
放在页面最顶部，使用注释或标注形式：
<code>
// 负责人：@张三
// 最后更新：2026-03-24
// 标签：{{tag>events core_mechanism}}
</code>
- **负责人**：对该页面内容负责的设计师
- **最后更新**：最近一次修改日期（格式 YYYY-MM-DD）
- **标签**：便于分类检索，多个标签用空格分隔

=== 8.1.2 概述 ===
用 1-2 句话说明这个系统的核心作用。**不要在此处罗列细节**，细节都在数据表中。

正确示例：
> 随机事件在每回合开始时按概率触发，玩家需要在限定时间内做出选择，获得相应奖励或惩罚。

错误示例：
> 随机事件有很多种，比如地磁扰动、数学家决斗……（后面开始列举具体事件，这应该放在数据表里）

=== 8.1.3 数据表 ===
使用 DokuWiki 表格语法，**每行一个设计条目**，列对应标准化模板的字段。禁止使用散落的列表或段落来描述多个条目。

表格语法说明：
- 表头行用 `^` 开头，普通行用 `|` 开头
- 列之间用 `^` 或 `|` 分隔
- 表头行与数据行之间不要空行

正确示例（事件表）：
<code>
^ ID ^ 名称 ^ 触发条件 ^ 权重 ^ 选项A ^ 选项A效果 ^ 选项B ^ 选项B效果 ^
| EVENT_FLOOD | 洪水 | 回合>5 & 有河流 | 5 | 加固堤坝 | 消耗木材50，避免损失 | 撤离 | 损失农田，人口安全 |
| EVENT_DROUGHT | 干旱 | 回合>8 & 无灌溉 | 4 | 打井 | 消耗资金30，粮食+20% | 求雨 | 消耗信仰10，概率成功 |
</code>

错误示例（散落列表）：
<code>
- 洪水事件：当回合大于5且有河流时可能出现。选择加固堤坝消耗木材50，避免损失；选择撤离会损失农田但人口安全。
- 干旱事件：……
</code>

=== 8.1.4 联动说明 ===
列出本系统与其他系统的关键联动，使用列表或简表形式。联动信息不应隐藏在数据表的某一行中，而应单独提炼。

示例：
<code>
=== 联动说明 ===
* 受科技影响：拥有“水利工程”后，“洪水”事件新增选项“修建大坝”。
* 影响资源：“干旱”事件会减少食物产量 50%，持续 3 回合。
* 与建筑联动：拥有“水井”建筑时，“干旱”事件触发概率 -50%。
</code>

=== 8.1.5 变更记录 ===
页面底部必须包含变更记录表，记录每一次重大修改。

格式：
<code>
=== 变更记录 ===
^ 日期 ^ 修改人 ^ 修改内容 ^
| 2026-03-24 | @张三 | 事件表新增 5 个条目 |
| 2026-03-20 | @李四 | 调整“洪水”触发条件，从“有河流”改为“有河流 & 未建堤坝” |
</code>

---

==== 8.2 不同类型页面的特殊要求 ====

=== 8.2.1 设计类页面（事件、科技、建筑、单位等） ===
- 数据表必须使用标准化模板的字段（参见第 3 章）
- 每行必须有一个唯一 ID，格式为 `类型_名称`，例如 `EVENT_FLOOD`、`TECH_IRON`、`BLD_FARM`
- 字段内容尽可能使用数值、布尔值或简短文本，避免长段落

=== 8.2.2 系统类页面（资源、指标等） ===
必须包含以下子章节：
- **数值范围与默认值**（如稳定度 0-100，初始 60）
- **获取/消耗方式**：使用表格列出所有来源和去向
- **效果**：说明如何影响其他系统

资源页面示例结构：
<code>
===== 食物 =====

=== 定义 ===
基础生存资源，用于维持人口和部分建筑的运作。

=== 数值 ===
* 存储上限：500（可通过仓库升级提升）
* 每回合自然消耗：人口 × 2
* 每人口每回合最低需求：2，不足时人口下降

=== 获取方式 ===
^ 来源 ^ 基础产量 ^ 影响因素 ^
| 农场（基础） | 10/回合 | 土壤肥力、科技加成、稳定度 |
| 随机事件“丰收” | 50（一次性） | 触发条件见事件表 |

=== 消耗方式 ===
^ 去向 ^ 数量 ^ 条件 ^
| 人口维护 | 人口 × 2/回合 | 每回合自动 |
| 建筑维护 | 5/建筑/回合 | 研究所、实验室等 |

=== 联动 ===
* 科技“轮作”：农场产量+15%
* 稳定度：稳定度低于30时，食物产量-20%
</code>

=== 8.2.3 索引类页面（如系统总览、TODO列表） ===
- 使用列表或表格，每个条目必须链接到具体页面
- TODO 列表中每项任务必须指明负责人和截止日期

---

==== 8.3 格式与语法规范 ====

=== 8.3.1 标题层级 ===
DokuWiki 使用等号表示标题，等号数量表示层级：
<code>
====== 一级标题 ======   （页面标题）
===== 二级标题 =====     （章节标题）
=== 三级标题 ===         （小节标题）
</code>
- 不要跳级使用（例如二级下面直接用四级）
- 每个页面有且只有一个一级标题

=== 8.3.2 表格 ===
- 使用 `^` 表示表头，`|` 表示普通行
- 表头行与数据行之间不要空行
- 如果表格过长，考虑拆分为多个小表

示例：
<code>
^ 列1 ^ 列2 ^ 列3 ^
| 数据1 | 数据2 | 数据3 |
| 数据4 | 数据5 | 数据6 |
</code>

=== 8.3.3 列表 ===
- 无序列表使用 `*` 或 `-`
- 有序列表使用 `-`（DokuWiki 会自动编号）
- 列表项之间不要空行，除非需要分段

示例：
<code>
* 第一项
* 第二项
  * 子项
* 第三项
</code>

=== 8.3.4 内部链接 ===
- 使用 `[[页面名|显示文字]]` 创建内部链接
- 链接到其他命名空间时使用 `[[命名空间:页面名|显示文字]]`
- 重要页面之间必须互相链接，避免孤岛页面

示例：
<code>
详见 [[designs:events|事件系统]]。
</code>

=== 8.3.5 标签 ===
在页面底部添加标签，格式：`{{tag>标签1 标签2 标签3}}`

常用标签：
* `mechanisms` - 核心机制
* `events` - 事件系统
* `tech` - 科技树
* `buildings` - 建筑
* `resources` - 资源
* `wip` - 进行中
* `review` - 待评审

---

==== 8.4 页面命名与组织 ====

=== 8.4.1 命名规则 ===
- 使用英文小写，单词间用下划线分隔：`research_tree`、`game_mechanisms`
- 不要使用中文文件名（但页面标题可以用中文）
- 保持简洁，体现内容

=== 8.4.2 目录结构 ===
<code>
designs/                # 设计文档根目录
  ├── game_mechanisms   # 核心机制总览
  ├── events            # 事件系统
  ├── research_tree     # 科技树
  ├── buildings         # 建筑系统
  ├── resources         # 资源系统
  ├── game_index        # 游戏指标
  ├── map_design        # 地图设计
  └── todo_list         # 待办事项
</code>

=== 8.4.3 页面引用 ===
在相关页面之间使用 `[[...]]` 建立双向链接，例如事件页面应链接到科技页面，科技页面也应链接回事件页面。

---

==== 8.5 质量检查清单 ====

在提交或更新页面前，请逐项检查：

- [ ] 页面顶部有负责人和最后更新日期（使用注释）
- [ ] 概述清晰，1-2 句话
- [ ] 数据表使用标准模板字段，每行一个条目
- [ ] 所有数据条目都有唯一 ID
- [ ] 联动说明部分列出了至少 2-3 个与其他系统的关系
- [ ] 页面底部有变更记录表，本次修改已记录
- [ ] 使用了正确的标题层级（页面一级，章节二级，小节三级）
- [ ] 添加了合适的标签（`{{tag>...}}`）
- [ ] 页面链接正确，没有断链
- [ ] 没有使用 <nowiki><del></nowiki> 或其他临时标记（待填内容应明确标注“待定”）


==== 8.6 反面案例 vs 正面案例 ====

=== 8.6.1 事件页面 ===

**反面案例**（常见错误）：
<code>
- Geomagnetic Disturbance
· Historical Background: ...
· Buffs/Debuffs: <del>...</del>
· Description: ...
</code>
问题：没有数据表，字段混乱，无法批量导入。

**正面案例**（符合规范）：
<code>
// 负责人：@Oscar
// 最后更新：2026-03-24
// 标签：{{tag>events}}

===== 随机事件 =====

=== 概述 ===
随机事件在每回合开始时按概率触发，玩家需要在限定时间内做出选择，获得相应奖励或惩罚。

=== 事件数据表 ===
^ ID ^ 名称 ^ 触发条件 ^ 权重 ^ 描述 ^ 选项A ^ 选项A效果 ^ 选项B ^ 选项B效果 ^ 影响链条 ^
| EVENT_SOLAR_1859 | 地磁扰动 | 回合>10 & 科技“电报”已研究 | 5 | 指南针乱转，电报机火花四溅…… | 记录现象 | 地磁学进度+25% | 修复设备 | 稳定度+10，资金-50 | 解锁事件“太阳黑子研究” |
| EVENT_MATH_DUEL | 数学家决斗 | 拥有至少2名数学家 | 4 | 两位数学家公开挑战…… | 担任裁判 | 胜者领域+25%，败者-15% | 私下调解 | 双方-5%，避免冲突 | 若选择裁判，后续事件“学术派系”触发概率+30% |

=== 联动说明 ===
* 受科技影响：“电磁学”可解锁“地磁扰动”事件的额外选项。
* 影响资源：“数学家决斗”可能消耗科研点或产生科研点。
* 与建筑联动：拥有“大学”时，“数学家决斗”触发概率 +50%。

=== 变更记录 ===
^ 日期 ^ 修改人 ^ 修改内容 ^
| 2026-03-24 | @Oscar | 从散落列表改为表格格式，新增联动说明 |
</code>

=== 8.6.2 资源页面 ===

**反面案例**：
<code>
====== Resources ======
====== Food ======
Produced from farms, it is essential for growth.
</code>
问题：没有数值、没有获取消耗细节、没有联动。

**正面案例**：
<code>
// 负责人：@Jack
// 最后更新：2026-03-24
// 标签：{{tag>resources}}

===== 食物 =====

=== 定义 ===
基础生存资源，用于维持人口和部分建筑的运作。

=== 数值 ===
* 存储上限：500（可通过仓库升级提升）
* 每回合自然消耗：人口 × 2
* 每人口每回合最低需求：2，不足时人口下降

=== 获取方式 ===
^ 来源 ^ 基础产量 ^ 影响因素 ^
| 农场（基础） | 10/回合 | 土壤肥力、科技加成、稳定度 |
| 随机事件“丰收” | 50（一次性） | 触发条件见事件表 |
| 贸易 | 可变 | 需要商路 |

=== 消耗方式 ===
^ 去向 ^ 数量 ^ 条件 ^
| 人口维护 | 人口 × 2/回合 | 每回合自动 |
| 建筑维护 | 5/建筑/回合 | 研究所、实验室等 |
| 事件选项 | 视事件而定 | 见事件表 |

=== 联动 ===
* 科技“轮作”：农场产量+15%
* 科技“化肥”：农场产量+30%
* 稳定度：稳定度低于30时，食物产量-20%
* 事件“蝗灾”：所有农场产量-50%，持续5回合

=== 变更记录 ===
^ 日期 ^ 修改人 ^ 修改内容 ^
| 2026-03-24 | @Jack | 初版创建 |
</code>

---

==== 8.7 总结 ====

遵循以上 DokuWiki 语法规范，你的 wiki 页面将具备：

* **可读性**：结构清晰，任何人都能快速找到关键信息
* **可维护性**：变更记录可追溯，负责人明确
* **可导入性**：数据表可直接转换为游戏数据格式
* **一致性**：所有页面风格统一，降低认知负担

**记住：写 wiki 不是为了写文章，而是为了给开发和未来的自己提供一份可以直接使用的设计蓝图。**
